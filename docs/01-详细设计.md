# AI 模拟面试器 · 详细设计

> 桌面端可执行程序（Windows），Python 3.11 + PySide6，本地 SQLite 存储，接入讯飞实时语音转写、讯飞超拟人语音合成、OpenAI 兼容大模型接口。

---

## 1. 目标与范围

### 1.1 核心目标

做一台"能陪你练满 20 分钟、会追问、会打分"的私人面试官。用户导入目标岗位的 JD 和自己的简历，程序生成一套针对性问题，用拟人化的语音提问，听用户口头作答并实时转成文字，像真实面试一样层层追问，结束后产出一份可执行的复盘报告。

### 1.2 功能清单

| 编号 | 功能 | 说明 | 优先级 |
|---|---|---|---|
| F1 | JD 导入 | 支持粘贴文本、上传 txt/md/pdf/docx，自动结构化解析 | P0 |
| F2 | 简历导入 | 同上，自动提取项目经历、技术栈、量化成果 | P0 |
| F3 | 出题 | 基于 JD 与简历的交叉分析，生成 18 个主问题 + 12 个备用题 | P0 |
| F4 | 语音问答 | 面试官 TTS 播报提问，面试者麦克风作答 | P0 |
| F5 | 实时转写 | 作答过程中文字逐字上屏，延迟约 300ms | P0 |
| F6 | 动态追问 | 根据回答质量决定追问 / 换角度 / 下一题 | P0 |
| F7 | 对话历史 | 全程对话实时可见，可回滚查看，落库持久化 | P0 |

- 不做浏览器版本、不做 Web 服务端
- 不做多人同时面试、不做账号体系
- 不做摄像头表情分析（v2 再议）

## 2. 技术选型

| 关注点 | 选择 | 理由 |
|---|---|---|
| GUI | PySide6（Qt 6 Widgets） | 原生窗口，无 Chromium 依赖，控件成熟，支持 QSS 主题化 |
| 麦克风采集 | sounddevice（PortAudio） | 直接拿到 16k/16bit/单声道 PCM 帧，无需转码 |
| 语音识别 | 讯飞实时语音转写 RTASR（WebSocket 流式） | 边说边出字，中文准确率高 |
| 语音合成 | 讯飞超拟人语音合成（WebSocket 流式） | 口语化韵律，最接近真人；可降级到标准合成 |
| 大模型 | OpenAI 兼容 `/chat/completions`（SSE 流式） | 一套代码适配 DeepSeek、通义、Kimi、智谱、星火、OpenAI |
| 存储 | SQLite（stdlib sqlite3，WAL 模式） | 零部署，单文件，事务可靠 |
| 文档解析 | pypdf、python-docx | PDF 与 Word 简历解析 |
| 打包 | PyInstaller `--onedir` + zip | 绿色免安装，解压即用，启动快 |

**音频链路刻意全程使用裸 PCM（raw），不引入 ffmpeg / pydub**：TTS 请求 `encoding=raw`，直接得到 PCM 流喂给 sounddevice 播放，省掉解码依赖，打包体积和失败点都更少。

## 5. 外部接口

### 5.1 讯飞实时语音转写 RTASR

**鉴权（HMAC-SHA1，用 APIKey）**

三步，**中间那步 MD5 不能省**，省了服务端就报 `illegal signa`：

```python
ts = int(time.time())
base = f"{app_id}{ts}"
digest = hashlib.md5(base.encode()).hexdigest()          # 1) MD5，结果转十六进制字符串
mac = hmac.new(api_key.encode(), digest.encode(), hashlib.sha1).digest()  # 2) HmacSHA1
signa = base64.b64encode(mac).decode()                   # 3) Base64
url = f"wss://rtasr.xfyun.cn/v1/ws?appid={app_id}&ts={ts}&signa={quote(signa)}&lang=cn"
```

已知向量（官方文档示例，可用来验证实现）：

| 输入 | 值 |
|---|---|
| appid | `595f23df` |
| ts | `1512041814` |
| apiKey | `d9f4aa7ea6d94faca62cd88a28fd5234` |
| MD5(appid+ts) | `0829d4012497c14a30e7e72aeebe565e` |
| **signa** | **`IrrzsJeOFk1NGfJHW6SkHUoN9CU=`** |

注意 `signa` 里带 `+ / =`，放进 URL 必须 `quote()` 完整转义。

**音频约束（必须严格遵守）**

- 采样率 16000 Hz、16 bit、单声道、PCM
- 每 40ms 发送 1280 字节，即每秒 32000 字节
- 发送节奏快于实时会导致服务端拒收，慢于实时会累积延迟
- **15 秒内没有音频上传，服务端主动断开**（37005）
- 实现方式：采集回调把 PCM 放入 `queue.Queue(maxsize=50)`，上传线程按 `time.monotonic()` 对齐节奏取帧
- 设备若开不了 16k（如本机默认 44.1k），退回默认采样率并线性插值重采样，**位置指针必须跨块保持**，否则块边界丢样本、累积错位

**返回解析**

外层是二段 JSON：

```json
{"action":"result","code":"0",
 "data":"{\"cn\":{\"st\":{\"bg\":\"0\",\"ed\":\"0\",\"rt\":[{\"ws\":[{\"cw\":[{\"w\":\"我\",\"wp\":\"n\"}]}]}],\"type\":\"1\"}},\"seg_id\":5}",
 "desc":"success","sid":"rta0000..."}
```

- `data` 是**字符串**，需二次 `json.loads`
- `cn.st.rt[].ws[].cw[0].w` 依次拼接即当前句文本
- **`cn.st.type`**：`0` = 本句最终结果，`1` = 中间结果。中间结果会把**整句重发**而不是增量，所以按 `seg_id` 覆盖存储、不要追加
- `wp`：`n` 普通词 / `s` 语气词 / `p` 标点
- 全文 = 各 `seg_id` 文本按序号拼接

注意：`ls` 是语音听写（IAT）的字段，RTASR **没有**这个字段，别混。

**收尾**：发送二进制 `{"end": true}`，服务端会把剩余结果推完后主动断开。每轮回答开一条新连接，避免上一轮残留文本混入。

**静音自动结束**：只有「检测到说过话」之后才开始计静音，否则用户刚点开按钮想一下就被掐断。另外单条回答设 90 秒上限，防止忘点结束一直占着连接。

### 5.2 讯飞超拟人语音合成

**地址**：`wss://cbm01.cn-huabei-1.xf-yun.com/v1/private/mcd9m97e6`

**鉴权（HMAC-SHA256，用 APISecret + APIKey）**

```python
date = formatdate(timeval=None, localtime=False, usegmt=True)
origin = f"host: cbm01.cn-huabei-1.xf-yun.com\ndate: {date}\nGET /v1/private/mcd9m97e6 HTTP/1.1"
sig = base64.b64encode(hmac.new(api_secret.encode(), origin.encode(), sha256).digest()).decode()
auth_origin = (f'api_key="{api_key}", algorithm="hmac-sha256", '
               f'headers="host date request-line", signature="{sig}"')
authorization = base64.b64encode(auth_origin.encode()).decode()
url = f"{endpoint}?authorization={authorization}&date={quote(date)}&host=cbm01.cn-huabei-1.xf-yun.com"
```

**请求体**

```json
{
  "header": { "app_id": "<APPID>", "status": 2 },
  "parameter": {
    // 只有 x4 系列认 oral。x5/x6 带上会被参数校验拦下，必须按 vcn 前缀决定发不发
    "oral": { "oral_level": "mid" },
    "tts": {
      "vcn": "x6_lingxiaoxuan_pro",
      "speed": 50, "volume": 60, "pitch": 50,
      "bgs": 0, "reg": 0, "rdn": 0, "rhy": 0,
      "audio": { "encoding": "raw", "sample_rate": 24000, "channels": 1, "bit_depth": 16 }
    }
  },
  "payload": {
    "text": { "encoding": "utf-8", "compress": "raw", "format": "plain", "status": 2, "text": "<base64>" }
  }
}
```

**返回**：`payload.audio.audio` 为 base64 PCM，`header.code == 0` 且 `payload.audio.status == 2` 表示结束。二进制内容直接进播放队列。

**降级**：`mode=standard` 时改走 `wss://tts-api.xfyun.cn/v2/tts`，鉴权同上一套签名规则（host 与 request-line 换成 tts-api.xfyun.cn 与 `/v2/tts`），audio 参数放在 `business.aue`（设为 `raw`）与 `business.auf`（`audio/L16;rate=16000`）。超拟人音色（`x4_`/`x5_`/`x6_` 前缀）在标准接口里不存在，必须换成 `aisjiuxu`。

### 5.3 发音人清单

超拟人**按发音人逐个授权**：控制台里能看到「已开通」不代表应用绑定成功，调用仍可能回 11200。这几个是控制台的默认免费音色，开通率最高：

| vcn | 名称 | 性别 | 用途 |
|---|---|---|---|
| `x6_lingxiaoxuan_pro` | 聆小璇 | 女声 | 交互聊天，**默认** |
| `x6_lingfeiyi_pro` | 聆飞逸 | 男声 | 交互聊天 |
| `x6_lingxiaoyue_pro` | 聆小玥 | 女声 | 交互聊天 |
| `x6_lingyuyan_pro` | 聆玉言 | 女声 | 交互聊天 |
| `x5_lingxiaotang_flow` | 聆小糖 | 女声 | 语音助手 |
| `x6_gaolengnanshen_pro` | 高冷男神 | 男声 | 角色配音 |
| `aisjiuxu` | 许久 | 男声 | 标准合成兜底（无需单独开通） |
| `aisxping` | 小萍 | 女声 | 标准合成兜底 |

注：控制台的 `chars.total` 是计费项（按字符计费），不是发音人，不能写进 vcn。

**三级兜底**，保证面试官一定能开口：

1. 音色级：当前音色回 11200/参数错误 → 自动换 `x6_lingxiaoxuan_pro` 重试，协议仍是超拟人，界面提示「音色 X 不可用，已改用聆小璇」
2. 编码级：`raw` 被拒 → 换 `lame` 并在本地用 miniaudio 解回 PCM
3. 协议级：超拟人整体不可用 → 走标准合成，`vcn` 强制 `aisjiuxu`

**音色探测**：设置页「检测全部音色」与 `tools/tts_probe.py` 逐个发一句 12 字短文本，直接列出哪个 vcn 能用、哪个回什么码，用于定位授权问题。老配置里的 `x4_` 音色在启动时自动迁移到 `x6_lingxiaoxuan_pro`。

### 5.4 大模型

标准 OpenAI 兼容协议：

```python
POST {base_url}/chat/completions
{
  "model": model,
  "messages": [...],
  "stream": true,
  "temperature": 0.7,
  "max_tokens": 1024,
  "response_format": {"type": "json_object"}   # 仅结构化环节使用，失败时自动去掉重试
}
```

需要 `response_format` 的服务商不在少数但并非全部支持，实现上做一次自动降级：请求失败且错误码提示不支持时，去掉该字段重发，并在提示词里强化 "只输出 JSON，不要 Markdown 代码块"。

预设服务商默认值：

| provider | base_url | 推荐 model |
|---|---|---|
| deepseek | https://api.deepseek.com/v1 | deepseek-chat |
| dashscope | https://dashscope.aliyuncs.com/compatible-mode/v1 | qwen-plus |
| moonshot | https://api.moonshot.cn/v1 | moonshot-v1-8k |
| zhipu | https://open.bigmodel.cn/api/paas/v4 | glm-4-plus |
| spark | https://spark-api-open.xf-yun.com/v1 | generalv3.5 |
| openai | https://api.openai.com/v1 | gpt-4o-mini |

## 7. 核心模块设计

### 7.1 线程模型

Qt 主线程只管界面。所有阻塞操作（麦克风、WebSocket、HTTP 流）都在 QThread 中执行，通过 Signal 回传。

```
主线程
 ├─ AudioCaptureThread   常驻，跑满整场面试；采集 → PCM queue
 ├─ AsrThread            每轮一条 RTASR 连接；PCM queue → 文本信号
 ├─ LlmThread            每次调用一个实例；HTTP SSE → token 信号
 ├─ TtsThread            常驻；句子 queue → PCM → 播放 queue
 └─ PlayerThread         常驻；PCM queue → sounddevice.OutputStream
```

信号清单：

| 信号 | 载荷 | 接收方行为 |
|---|---|---|
| `asr_partial(str)` | 当前句未定稿文本 | 更新 partial 气泡（不落库） |
| `asr_final(str)` | 定稿文本 | partial 转正式气泡，写 messages |
| `asr_error(str)` | 错误描述 | 顶部红条提示，转打字模式 |
| `llm_token(str)` | 增量文本 | 追加到面试官气泡 |
| `llm_done(dict)` | 完整结果 + 结构化字段 | 结束流式态，进入 TTS |
| `tts_state(str)` | `playing` / `idle` | 控制麦克风是否允许录音 |
| `level(float)` | 0–1 音量 | 驱动波形动画 |

**防串音规则**：面试官播报期间禁用采集（或采集但丢弃），避免把自己的声音录进去。TTS 播放结束后留 300ms 再开麦，等回声消散。

### 7.2 音频采集

```python
sd.InputStream(
    samplerate=16000, channels=1, dtype="int16",
    blocksize=1280,           # 40ms
    callback=self._on_audio,  # 回调里只做 queue.put_nowait
)
```

回调里**绝不做重活**（PortAudio 回调超时会爆音）。音量计算在消费线程做：取一帧 `int16` 的 RMS，映射到 0–1 后 emit。

设备选择：首次启动列出 `sd.query_devices()` 里的输入设备，默认选系统默认录音设备，设置页可切换。麦克风被拔掉时捕获异常，提示并保持会话不崩。

### 7.3 TTS 分句与播报队列

直接合成整段话会让首字延迟达到 2–3 秒。做法是**边收边切边合成**：

1. LLM 流式吐字时，累积缓冲区，遇到 `。！？；\n` 或累计超过 40 字就切一句
2. 每句立刻提交 TTS 合成，结果按序进播放队列
3. 播放线程连续消费，句与句之间的间隔由 PCM 拼接自然消除

暂停/打断：面试者点「跳过播报」或直接说话时，清空播放队列并停止当前流。

```python
def feed(self, delta: str):
    self.buf += delta
    while (idx := find_split(self.buf)) > 0:
        self.enqueue(self.buf[:idx]); self.buf = self.buf[idx:]
def flush(self):
    if self.buf.strip(): self.enqueue(self.buf); self.buf = ""
```

标点优先，不要按固定长度硬切，否则会出现"我 们今天"这种断词，拟人感全没了。

### 7.4 出题引擎 QuestionPlanner

**两阶段调用**，避免一次性塞太多内容导致质量下降：

阶段 A（并行两个请求）：`parse_jd` + `parse_resume`，各自输出结构化 JSON。

阶段 B：拿两份结构化结果 + 面试配置，一次性生成题库。

提示词要点（`prompts.py`）：

```
你是 <公司> <岗位> 的资深面试官，正在面试一位候选人。

【岗位要求】{jd_profile}
【候选人简历】{resume_profile}

请生成 {n} 道主面试问题，覆盖以下阶段并严格配比：
- opening 开场 1 题（自我介绍，结合简历定制）
- resume 简历深挖 {a} 题（必须锚定简历中的具体项目和技术选择，禁止泛泛而谈）
- jd 岗位匹配 {b} 题（逐条对照 must_have，覆盖度不低于 80%）
- closing 收尾 1 题（反问或职业规划）

要求：
1. 每题必须能追溯到 JD 或简历里的具体内容，拒绝"请介绍一下你的优缺点"这类通用题
2. 难度分布 3:5:2（易/中/难）
3. 为每题标注考察点 intent 和参考答案要点 reference_answer
4. 另生成 {m} 道备用题，用于时间富余时补充

只输出 JSON：{"questions":[{...}]}
```

生成结果写入 `questions` 表，`status=pending`。

**兜底**：若解析失败或返回数量不足 8 题，重试一次；仍失败则使用内置通用题库（按岗位大类分三套），并在界面提示"本次为通用题库，建议检查配置"。

### 7.5 面试导演 InterviewDirector

这是整个程序的大脑，负责「下一句说什么」。

**阶段状态机**

```
opening ──(1-2轮)──> resume ──(时间或题量)──> jd ──(剩余<3min)──> closing
   ↑                                                              │
   └────────────── extra（超时后的加分追问，可循环） ←────────────┘
```

阶段推进不只按题号，还按时间：resume 阶段最多占 40% 时长，到点强制进 jd。这样即使用户在某个项目上聊嗨了，也不会没机会覆盖 JD 要求。

**每轮调用的输入**

```python
messages = [
    {"role": "system", "content": interviewer_system_prompt(...)},
    *近 10 轮对话,          # 完整历史会超长，窗口滚动
    {"role": "user", "content": f"候选人刚回答：{answer}\n请决定下一步。"}
]
```

`interviewer_system_prompt` 动态注入：

```
当前已进行 {elapsed_min} 分钟，计划总时长 {planned_min} 分钟，剩余 {remain_min} 分钟。
当前阶段：{phase}。本阶段已完成 {done}/{total} 题。
当前问题追问层数：{depth}/{max_followups}。

【硬性规则】
- 剩余时间 > 3 分钟时，禁止输出 action=closing
- 追问层数已达上限时，禁止输出 action=followup
- 剩余时间 >= 3 分钟且问题已用完时，输出 action=next 并从备用题中挑一题
- 每次只问一个问题，不要一次抛出多个问题
- 口语化，像真人说话，句子短，不超过 60 字
- 不要复述候选人的回答，不要总结，不要评价
```

**追问判定策略**（写进提示词，同时代码侧兜底）

| 观察到的信号 | 决策 |
|---|---|
| 回答少于 30 字或明显敷衍 | followup，要求展开并举具体例子 |
| 提到技术选型但没讲 why | followup，追问取舍与替代方案 |
| 有量化数据但没说口径 | followup，追问数据来源与统计方式 |
| 回答里出现"我们团队"但没有"我" | followup，明确个人贡献 |
| 回答完整、有细节、有反思 | next，换下一题或换角度 |
| 答错但方向对 | hint，给一句提示后重新问 |

**代码侧兜底**（不能全指望模型听话）：

```python
decision = llm_decide(...)
if remain_min <= 1 and decision.action != "closing":
    decision = closing_decision()
if depth >= max_followups and decision.action == "followup":
    decision.action = "next"
if not question_bank.has_next() and remain_min > 3:
    decision.question = question_bank.next_spare()
```

### 7.6 时长保障机制

三重保险，缺一不可：

1. **题库冗余**：18 主 + 12 备，按每题 60–90 秒计算，最保守也有 18 分钟，加追问必然超 20 分钟
2. **时间注入**：每轮把剩余分钟写进提示词，让模型主动控制节奏
3. **代码守卫**：见 7.5 兜底逻辑，剩余时间不足时强制改变 action

满 20 分钟后**不自动结束**，切换 `extra` 模式继续加分追问，直到用户点结束或备用题耗尽（耗尽后模型现场生成新题）。

UI 上计时器超过 20 分钟后变为琥珀色并显示"已达标 · 可随时结束"，给用户明确的退出信号。

### 7.7 手动结束流程

点击「结束本轮」→ 弹出确认框：

```
本轮已进行 14 分 32 秒，未满计划的 20 分钟。
提前结束会以当前对话为准生成报告，可能影响评估完整度。

[ 继续面试 ]  [ 仍然结束 ]
```

确认后执行：

1. 置 `status=aborted`（满 20 分钟则为 `finished`），写 `duration_sec`
2. 停采集、停 ASR、清空 TTS 播放队列
3. 补一条 system 消息记录结束原因
4. 切到报告页，进度条显示"正在生成报告"，后台线程跑 `ReportGenerator`

报告生成期间用户可离开该页，完成后侧栏对应条目出现红点。

## 8. 关键流程

### 8.1 新建面试

1. 拖入或粘贴 JD → `doc_parser` 提取纯文本 → 顶部显示前 200 字预览
2. 同上导入简历
3. 填公司与岗位（可从 JD 自动猜测预填）
4. 显示"预计 20 分钟 · 18 题 · 男声/女声"
5. 点「开始面试」→ 两个并行 LLM 请求解析 → 出题 → 写库 → 跳面试页 → 面试官开场白（TTS 播报）

解析与出题期间显示骨架屏与进度文案（"正在分析岗位要求"→"正在拆解简历项目"→"正在准备问题"），通常 5–15 秒。

### 8.2 面试循环

```
播报问题 → 开麦采集 → ASR 流式上屏 → [静音 2s 或点击结束作答]
   → 定稿落库 → LLM 决策 → 追问 or 下一题 → 回到播报
```

任何环节超时（LLM 30s 无响应、ASR 10s 无结果）都降级：
- LLM 超时：用当前题目的 `reference_answer` 生成一句过渡语，跳到下一题
- ASR 超时：提示"没听清，可以打字补充"，切输入框

### 8.3 报告查看

历史页列表 → 点任一条 → 报告页。左侧雷达与总分，右侧 Tab 切换「亮点短板」「逐题点评」「JD 差距」「原始对话」。底部「导出 Markdown」「重新生成报告」。

重新生成会覆盖原报告，但保留旧 `markdown` 到 `data/reports_backup/`。

## 9. 异常与降级

| 场景 | 表现 | 处理 |
|---|---|---|
| 讯飞三元组错误 | 401/403 | 顶部提示"讯飞鉴权失败"，跳设置页 |
| 转写连接断开 | 无文本上屏 | 自动重连 2 次，仍失败则转打字模式 |
| 超拟人无权限 | 11200 | 自动降级 standard 模式并提示 |
| TTS 合成超时 | 无声音 | 5s 超时后跳过该句，文字照常显示 |
| 大模型 429 | 请求失败 | 指数退避重试 2 次，仍失败提示稍后再试 |
| 大模型返回非 JSON | 解析异常 | 抽取 JSON 片段重试；失败则用兜底决策 |
| 麦克风占用 | 打不开设备 | 提示换设备或关闭其他录音软件，可切打字 |
| 断电/崩溃 | 会话中断 | 启动时扫描 `status=running` 的记录，提示"上次面试未正常结束，是否恢复/生成报告" |
| 磁盘写入失败 | 保存报错 | 只读模式运行，提示检查权限，不阻塞面试 |

日志用 `logging` + `RotatingFileHandler`，落在 `data/logs/app.log`，保留 7 天。**日志里绝不打印 API Key 与 APISecret**，统一脱敏为 `sk-****abcd`。

### 12.1 M4 实现与设计的差异

设计阶段写的方案在实际对接时改了三处，记录在此以免后续误解：

**1. 超拟人接口的 `raw` 编码存在文档冲突，改为三级降级**

讯飞主站文档推荐 `encoding=raw`，但超拟人 V3 的参数表里只列了
lame/speex/opus。赌单一编码会在用户那边直接没声音，所以改成逐级尝试：

| 顺序 | 协议 | 编码 | 失败后的动作 |
|---|---|---|---|
| 1 | 超拟人 cbm01 | raw | 参数类错误 → 换 lame 再试 |
| 2 | 超拟人 cbm01 | lame | 本地 miniaudio 解回 PCM；解码失败 → 降级 |
| 3 | 标准合成 v2/tts | raw（aue=raw, auf=audio/L16） | 仍失败则报错 |

降级只发生一次并记在 `TTSEngine.degraded` 上，界面提示"已改用标准发音人"，
之后不再每句话都先失败一遍。

**2. 播报状态不靠播放器回调，改用播放线程心跳**

`PCMPlayer` 播完最后一帧时不会主动通知（它只在喂数据时报"在播"），
最初的设计依赖这个回调，结果状态胶囊会永远亮着。现在由播放线程在
"无在途合成 + 无待播数据 + 播放器已停"三个条件同时成立时才广播 `idle`，
并用 `_idle_announced` 保证只广播一次。

**3. 每次合成一句，独立建连**

超拟人接口的 `payload.text.status=2` 是一次性投递，一个连接只服务一次合成。
考虑到一句话 40 字约 8 秒音频、合成只要 0.5 秒，用 3 个并发线程提前合成
后续句子就足够掩盖握手开销，不需要在一个连接里做双向流式，复杂度低很多。
